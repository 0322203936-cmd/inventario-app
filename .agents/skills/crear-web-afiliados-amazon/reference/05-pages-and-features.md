# Pages & Features — generated from data, richer than the reference

Every page here is a **view over `window.__DB__`**. No product is hand-written.
This file specifies each page and the signature features (comparator, radar,
spec table) — all improved past the reference site's 30%.

Rendering pattern: HTML ships the page shell + SEO/legal text (works with JS
off); `main.js` (IIFE) reads `window.__DB__` and mounts the data-driven parts
(`04-critical-gotchas.md` D.3 — idempotent mounts, `safe()` wrappers).

---

## The ficha (product page) — the big upgrade

The reference had a thin card. The target ficha has, top to bottom:

1. **Gallery** — the WebP images (Group A), thumbnails + main, keyboard/swipe.
2. **Header** — name, brand, star rating + review count, price with offer badge
   and the «precio orientativo · fecha» note (invariant 6), the big **«Ver en
   Amazon»** button using `affiliate_url` (invariant 1). Repeat the button after
   each major section — buy intent is highest after reading.
3. **Radar chart** — the 5-7 scores (Group D) as a filled polygon, labelled
   "valoración del editor". This is the at-a-glance identity of the product.
4. **Spec table** — all Group C fields, grouped (motor, batería, medidas,
   equipamiento), `null` → "—", units shown, `specs_extra` in an "otros datos"
   sub-section. Dense, scannable, the reference's best idea kept.
5. **Editorial body** — `cuerpo_editorial`: real paragraphs (the "blog touch"
   the reference lacked). Then **pros/contras** as two columns and **`ideal_para`**
   as a highlighted line.
6. **Reviews** — `resenas_resumen` + a few scraped reviews (author, stars, text),
   labelled as from Amazon.
7. **Comparar** — a button to add this product to the comparator, and a
   "productos similares" strip (same category, nearby price).
8. **Affiliate disclosure** — visible (invariant 5).

JSON-LD `Product` with only real scraped values (name, brand, offers,
aggregateRating). One ficha per record, generated — never per-product HTML.

## The comparator — keep and improve

The feature the user loves. Requirements:

- Select **2 to N** products (from any ficha's «comparar», or a search box on
  the comparator page — reuse the reference's comparator search idea).
- **Side-by-side spec table**: rows = schema fields, columns = products; the
  best value per numeric row highlighted (min or max depending on the field —
  more autonomy good, more weight bad; the schema says which).
- **Radar overlay**: all selected products' score polygons on one chart,
  distinct colors — the visual gut-check.
- Each column has its own **«Ver en Amazon»** (correct affiliate link).
- Deep-linkable: selected ids in the URL hash so a comparison can be shared.
- Only compares within a niche (multi-niche shops).

## The charts — real, vendored, light

- **Radar** (ficha + comparator) and simple **bars** (rankings). Use a small
  vendored chart lib (`14`/`descargar-librerias.py`) via the ESM bridge, OR —
  preferred for a radar — hand-draw it in ~60 lines of canvas/SVG (no lib): the
  reference used a custom RadarChart component and it's not much code. Fewer
  dependencies = fewer runtime risks (`04` invariants).
- Charts read scores from the data; if a product lacks a score axis, the polygon
  point sits at 0 and the UI notes it, never fakes it.

## Home

Hero with the site's promise, a **"cómo elegimos"** trust block (explains the
scores = credibility + SEO), featured products (`isFeatured`), newest, category
entry cards, and a strip to the buying guides. Everything from data except the
static trust copy.

## Category / niche pages

One per meaningful `category`/`tipo_uso`. Filterable/sortable grid (by price,
autonomy, score…) built from the data, an intro paragraph per category
(editorial), and links into the relevant buying guide.

## Buying guides / rankings (the SEO engine)

- Guides: "mejor bici eléctrica para ciudad 2026" — editorial intro + a
  generated shortlist of matching fichas with why-each, cross-linked.
- Rankings: "top 5 por autonomía" — a list generated by sorting on a field/score.
- `FAQPage` / `ItemList` JSON-LD. These pull the search traffic; fichas convert
  it. Build at least one guide; offer more.

## Ofertas

Records where `discountedPrice < retailPrice`, sorted by discount %, each with
the offer badge and buy button. Optionally an "oferta del día" slot the user
can pin.

## Legal & disclosure (required)

- **Aviso de afiliados** on every page (footer) + a dedicated page: states the
  site earns commissions and the Amazon trademark notice (invariant 5).
- Privacy + cookies skeletons. Contact. "Cómo elegimos" methodology.

## Range map (optional, high-impact)

For niches with a range/battery/runtime spec, add the **reachable-area map** —
pick a point, see how far each product goes as a real street-shaped isochrone,
with an ida/vuelta toggle, overlaid in the comparator. Keyless, front-end only.
Full spec in `14-mapa-autonomia.md`. Offer it; build on request.

## Generator: build the pages FROM the data (the reliable pattern)

Don't render fichas at runtime from JS (that breaks "works without JS" and SEO),
and don't hand-write product HTML (that breaks "data-driven"). Do both correctly
with a small **build script** — `tools/build_site.py` (Python), run after every
data change:

1. Reads `datos/productos.json`.
2. Writes **one static HTML file per record** (`bici-<slug>.html`) with the core
   facts baked into the HTML (name, brand, price, buy button with the exact
   `affiliate_url`, spec table, editorial, disclosure, JSON-LD) — so it renders
   with JS off and is perfect for SEO — plus `data-*` hooks for JS to enrich.
3. Writes the category pages, home, comparator shell, guides, ofertas, legal.
4. Writes `lib/db.js` (`window.__DB__ = {productos:[…]}`) for the JS layer
   (comparator, radar, filters, map).
5. Bumps a single `VER` constant → every page references `styles.css?v=VER`,
   `main.js?v=VER`, `lib/db.js?v=VER`. **Bump VER on every build** (`04` E.5).

Shared partials in the script (header, footer, product card, spec table, buy
button, price) keep it DRY. Adding a product = edit the JSON, re-run the build,
re-deploy. No page is ever hand-edited. This is the single most important
structural decision — it's what makes the site scale and stay consistent.

**Price display:** show the scraped price (ES format `1.299 €`); if
`discountedPrice < retailPrice`, show the strike-through and the item flows into
Ofertas automatically. If there's no price, "Ver en Amazon". Once you show
prices, label buy buttons **"Ver en Amazon"** (not "Ver precio…").

## Definition of done (pages)

- [ ] Every product renders from data; **no product HTML is hand-written** —
      it's generated by the build script (generated files DO contain the names,
      that's correct; what's forbidden is authoring a page per product by hand).
- [ ] Comparator works with 2 and with 4 products; best-value highlight correct;
      radar overlay renders; each buy button has the right affiliate link.
- [ ] A ficha shows: gallery, radar, full spec table (nulls as "—"), editorial
      body, pros/contras, reviews, disclosure, JSON-LD with only real values.
- [ ] At least one buying guide + ofertas + category pages exist and cross-link.
- [ ] JS off → ficha core facts, prices, legal and disclosure still render.
- [ ] Affiliate disclosure on every page. Prices carry a date.
- [ ] Console clean; `?v=` bumped; previewed over http (charts need it).
